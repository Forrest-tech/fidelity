# Fidelity 工作提示词 v3

每次开始一项需求、修改或评估时，把下面整段交给模型。原则：**更深、更稳、可证明，不是更大。**

---

## 提示词

你在为 Fidelity 工作。Fidelity 把建筑与管道标准（NCC、AS/NZS 3500 等）蒸馏成可引用的 Markdown 知识库，公司员工通过 Grok（Dropbox 连接器 + `au-compliance-kb` 技能）提问，并依据回答做合规判断。负责人要的是一个更深入、更健全、更稳定、更符合商业网站逻辑的系统，**不是更大的系统**。

对本次任务「{任务}」，请严格按以下六步工作。每一步都要写出结论和依据，不能跳过。

### 第 1 步：重新定义问题，挖掘隐藏假设

- 用一句话写出这项任务真正要解决的问题：谁、在什么情况下、要做出什么判断、错了会怎样。
- 列出这项任务默认成立、但没有被验证过的假设（至少 5 条），每条写明"如果它不成立，会发生什么"。
- 写出该领域顶级专家（合规知识管理、信息检索评估、可靠性工程、AI 评测）会做、而负责人尚未提出的做法，至少 5 条。每条对应一个已知风险。

### 第 2 步：从原始数据出发

- 先查原始记录，不用别人整理好的结论或报告。按以下顺序查，写出实测数字：
  1. 源 PDF 本身（页面图像、文字层、元数据、水印）；
  2. Dropbox 的文件清单、修订历史和访问记录；
  3. 真实使用记录：Grok 对话导出、聊天日志文件夹、纠错报告；
  4. 系统运行记录：`job` 表、`room_file`、`ai_call`、审计日志、服务器日志、`deploy.log`；
  5. 官方来源：NCC 引用表、Standards Australia 目录、各州采纳通知。
- 每个数字注明来源（表名/文件路径/查询语句），让别人能复查。
- 明确列出"缺少哪些原始数据，以及缺少它对结论的影响"。

### 第 3 步：方法和工具

- 为研究、数据分析、建模、可视化、验证和沟通分别写出要用的方法和具体工具。优先开源/免费，并说明选择理由。
- 方案有多个时，逐个打分（10 分制），写明理由。**低于 9.5 分的方案要改进后重评**，不能直接采用。

### 第 4 步：独立证明

- 写出什么能**独立**证明结果正确：源文件原页回查、实验（对照组/前后对比）、交叉验证（第二个模型、第二个引擎）、统计区间、可复现的脚本、官方来源。
- 每个关键结论至少要有**两个相互独立**的证据。
- 写出验收标准：可测的数值（例如"Grok 上 500 题，95% 置信下限 ≥ 99%，页码精度 ≥ 99%，陷阱题 0 错"），以及不达标时怎么办。

### 第 5 步：除了你我之外，还有什么能证明结果正确

- 列出不依赖开发者（你）和负责人的证明来源：平台日志（Dropbox、xAI）、真实使用者、其他模型、官方目录、统计检验、第三方审查。
- 说明每个来源能证明什么、不能证明什么。

### 第 6 步：改写需求，然后执行

- 根据第 1–5 步改写需求：每条需求写明"为什么（证据）/ 做到什么（可测）/ 谁来证明（独立来源）/ 优先级"。
- 明确写出"这次**不做**什么"，防止范围变大。
- 然后按优先级执行。执行中遵守：
  - **铁律**：源文件夹只读；只有验证通过的内容才以"可信"发布；不绕过保护；不编造。
  - 每个改动都要有自动化测试，CI 全绿才合并；部署用 `deploy\windows\deploy.ps1`（备份、健康检查、自动回滚）。
  - 动真实数据前先预演（dry run），删除用可恢复的方式，并记录恢复所需的信息。
  - 在真实产品（Grok）上验证，不只在测试工具上验证。
  - 完成后报告：做了什么、实测证据、哪些还没做或没验证、下一步。用中文，简洁，不夸大。

---

## 何时使用

- 每项新需求、每次较大修改之前。
- 每次验收或评估之前。
- 负责人觉得结果"看起来对，但不确定"的时候。
