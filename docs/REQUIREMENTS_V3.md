## 0. 问题重新定义

v1 的问题是"把 PDF 转成 Markdown"，v2 改成"让答案引用正确版本、条款、页码"。看完原始数据后，真正的问题是：

> **公司员工依据 AI 的回答做合规判断。系统要做到：答案可以逐字追溯到原文的那一页；系统知道自己什么时候不知道；任何错误都会被发现、记录，并且不再出现。**

这把重心从"转换质量"移到三件事：
- **可追溯**：引用精确到原页；
- **可观测**：真实使用情况看得见；
- **闭环**：错误被发现后进入回归，不再出现。

转换只是其中一环。

## 1. 原始数据告诉我们什么（2026-11-24 实测）

不用整理过的报告，直接查原始记录：

| 原始材料 | 实测结果 | 推翻了哪个隐藏假设 |
|---|---|---|
| Dropbox `/Library_Installation_Chat_Logs` | **共 4 个日志，其中 3 个是开发测试**。Grok 侧边栏里还有"Minimum Grade for 100 mm Sanitary Drain NSW"等真实对话，都没有存日志 | "员工每天在用，用法有记录"——**真实使用几乎看不见**；日志靠 AI 自觉保存，它经常不存 |
| Grok 实测回答（2026-11-23） | 数值、页码都对，但没输出"📁 Saved"，日志文件名格式不对 | "技能写了，AI 就照做"——**AI 不完全遵守说明** |
| 验收运行 `docs/acceptance/runs` | 316 题全部由 **DeepSeek** 通过测试工具回答；Grok 只测过约 25 题 | "测试工具上的分数 ≈ 员工用 Grok 的分数"——**测的不是实际使用的产品** |
| 验收失败明细 | 剩下 4–6 个错里，大多数看起来是"数值对、页码错"。**2026-11-24 复核更正**：引用页其实是对的，是判分程序把表格单元格换了顺序或带多余标点的引文判成"不在该页"。修正判分后为 313/316（99.1%，95% 区间 97.3–99.7%），严格页码精度 98.3%，真正"数值对、页码错"的只有 2 题；同时修掉了一个旧漏洞（近似匹配曾放过一个数字不同的引文） | "判分程序是对的"——**评测工具本身也要被检验** |
| Dropbox 全盘清单 | 源文件只有 **44 份 PDF**（AS 3500 39 份、NCC 2025 5 份），1.2 GB | "可以从源头重新蒸馏全部内容"——`Md_Library` 里旧的 **1,590 份文档在这里没有源文件**，既不能重新蒸馏，也不能回查原文 |
| 任务记录（`job` 表） | 31 次运行，**13 次出错（42%）**：共享链接失效 5、Dropbox 断线 2、Windows 文件锁/拒绝访问 2、磁盘满 1、进程被杀 2、下载 1 | "蒸馏是难点"——**基础设施才是最大的失败来源** |
| 服务器（2026-11-23） | 虚拟机重启后服务没有自己起来（计划任务只在登录时启动） | "部署了就一直在线"——**没有无人值守的可用性** |
| AI 建议（`ai_call` 表） | **504 条建议，人工决定了 0 条** | "AI 建议、人来确认"——**这个人工环节实际不存在** |
| 人工确认（`room_file`） | 27 份文件被确认，全部来自一次批量点击 | "每份都有人审"——**实际是批量放行** |
| 扫描件 | 3500.0/3500.4:2021 只有扫描件，识别率 84.7–95.9% | 扫描件靠审核达不到 99%（v2 已知） |

**结论**：系统的"转换"已经接近目标（文字版 PDF 验证 100%，问答 98.7%）。最薄弱的不是转换，而是：
1. 看不到真实使用；
2. 没在真正的产品（Grok）上验证；
3. 人工审核环节名存实亡；
4. 基础设施不稳；
5. 旧库无法验证。

## 2. 顶级专家会做、但还没被要求的事

| # | 专家做法 | 为什么（对应 §1 的证据） |
|---|---|---|
| E1 | **在真实产品上测**：验收和日常回归都直接跑在 Grok（同一模型、同一技能、同一 Dropbox 连接）上，测试工具只做辅助 | 316 题跑在 DeepSeek 上，不能代表 Grok |
| E2 | **不依赖 AI 自觉的使用记录**：用 Dropbox 自己的访问记录（哪个文件在什么时候被读取）和 Grok 的对话导出，作为使用和引用的客观证据 | AI 经常不存日志 |
| E3 | **以页码精度为主指标**：引用页 = 数值或引文实际所在页；每题都算 | 剩余错误主要是页码 |
| E4 | **按风险分级的人工审核**：只把高风险内容交给人（扫描件、数字不一致、表格、被 NCC 引用的条款），审核量可控，每次审核有记录 | 504 条建议 0 条被审，说明全量审核不可行 |
| E5 | **知识库按版本发布**：每次发布有版本号、变更清单（新增/修改/删除的条款）、验收分数，可一键回到上一版 | 现在的发布是逐文件替换，无法回答"上周和这周的库有什么不同" |
| E6 | **覆盖地图**：列出员工需要的标准和版本（以 NCC 引用表为准），对比库里实际有的，缺口一目了然 | 只有 44 份源文件；旧库 1,590 份无法验证 |
| E7 | **金丝雀监测**：每周自动用固定题集问 Grok，分数画成控制图；模型悄悄升级或技能被改时立刻发现 | AI 服务会不通知就更新 |
| E8 | **失效模式分析（FMEA）**：把每种已发生的故障列出来，给出发生频率、严重度、可发现度，按风险排序修 | 42% 的运行失败，原因分散 |
| E9 | **合规责任边界**：答案注明"决策辅助，不替代认证人员判断"；高风险问题（结构、消防、燃气）要求人工复核 | 答案用于合规判断 |
| E10 | **文档内的提示注入防护**：标准原文或网页快照里如果有"忽略之前的指令"之类的文字，不能影响 AI | 已有标记，需要红队测试证明 |

## 5. 什么能独立证明结果正确（不依赖开发者，也不依赖负责人）

| 证据来源 | 证明什么 | 为什么独立 |
|---|---|---|
| 源 PDF 的那一页 | 引文和数值确实在那页 | 原文本身，程序自动比对 |
| Dropbox 访问记录 | AI 实际读了哪些文件 | Dropbox 平台记录，AI 无法伪造 |
| Grok 对话导出 | 员工真实问了什么、AI 真实答了什么 | 来自 xAI 平台 |
| 另一家 AI 模型 | 同题答案一致性 | 不同厂商、不同训练 |
| NCC 官方引用表 / Standards Australia 目录 | 版本是否现行、库里缺什么 | 官方来源 |
| 统计区间与控制图 | 99% 不是运气 | 数学，任何人可复算 |
| CI 复现 | 任何人拉代码都能重跑出同样分数 | 公开脚本、固定数据 |
